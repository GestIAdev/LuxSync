### 1.2 Referencia a Buffers DMX — ¿SAB o Copias?

| Componente | Buffer | Mecanismo | Origen del dato |
|---|---|---|---|
| `TickEngine.dmxWriter` | `DmxUniverseWriter` | SAB (`getDmxSab()`) | `new DmxUniverseWriter(getDmxSab())` — línea 45 |
| `TickEngine._universeSnapshots` | `Map<number, Uint8Array>` | **Copia intermedia** | `new Uint8Array(CHANNELS_PER_UNI)` — copia desde `egressBuf` en cada frame |
| `NodeResolver._universeBuffers` | `Map<number, Uint8Array>` | Pre-alloc in-place | Se escribe durante `resolve()`; se lee por `getUniverseBuffer()` |
| `HAL._lastUniverseBuffers` | `Map<number, Uint8Array>` | Copia deduplicación | Solo para legacy path |
| `UniversalDMXDriver.universeBuffers` | `Map<number, Buffer>` | Copia en `setUniverse()` | Recibe datos vía `USBDMXDriverAdapter` → `setUniverse()` |

**Conclusión:** El SAB (`DMX_UNIVERSE_SAB`) es el único buffer que cruza la frontera sin copia. Sin embargo, el `TickEngine` hace **una copia intermedia** (`_universeSnapshots`) antes de escribir al SAB. La razón: `NodeResolver.getUniverseBuffer()` devuelve un `Uint8Array` que puede ser mutado por `getSoftBlackoutUniverseBuffer()`, por lo que el SAB necesita un snapshot estable.

## TARGET 2: EL CEMENTERIO DE WORKERS

### 2.1 `openDmxWorker.ts` (WAVE 2021.5) — EL MEJOR CÓDIGO MUERTO

**Archivo:** `src/hal/drivers/strategies/openDmxWorker.ts`  
**Tipo de proceso:** `child_process.fork()` (NO `worker_threads`)  
**Estado:** **Abandonado**. Ningún archivo del proyecto ejecuta `fork()` sobre este script en la rama actual.

#### Payload Esperado
El worker espera **mensajes IPC vía `process.on('message')`**, NO `workerData`.

```ts
// Protocolo de mensajes (líneas 26–29, 687–727)
process.on('message', (msg: { type: string; portPath?: string; channels?: number[] }) => {
  switch (msg.type) {
    case 'CONNECT':       // { type: 'CONNECT', portPath: string, refreshRate?: number, breakMode?: 'set'|'baudrate' }
    case 'UPDATE_BUFFER': // { type: 'UPDATE_BUFFER', channels: number[] }  ← array plano, NO ArrayBuffer
    case 'RESET_BUFFER':  // { type: 'RESET_BUFFER' }
    case 'DISCONNECT':    // { type: 'DISCONNECT' }
  }
})
```

**Compatibilidad con SAB:** **CERO**. El worker no conoce `SharedArrayBuffer`, `Atomics`, ni `DmxUniverseReader`. Espera un array plano de números (`number[]`) vía IPC, que el `UniversalDMXDriver` le enviaba en `sendAll()` a través de `strategy.send(null, buffer, universe, log)`.

#### Lógica de BREAK y Timing
El worker contiene la implementación **más precisa** de bit-banging DMX en toda la codebase:

| Aspecto | Implementación | Líneas |
|---|---|---|
| Prioridad OS | `os.setPriority(PRIORITY_HIGHEST)` | 51–69 |
| BREAK exacto | `spinWaitNs(BREAK_NS)` donde `BREAK_NS = 110_000` (110µs) | 494–504 |
| MAB exacto | `spinWaitNs(MAB_NS)` donde `MAB_NS = 20_000` (20µs) | 508 |
| Pacing de frame | `process.hrtime.bigint()` + adaptive `minFrameNs` | 107–109 |
| Scheduling | `setImmediate()` con spin-wait previo si falta ≤5ms | 414–467 |
| Double buffer | `dmxBuffer.copy(dmxSendBuffer)` antes de `port.write()` | 530–535 |
| Baudrate-switch | Sí, completo: `update(76923)` → `write(0x00)` → `drain()` → `update(250000)` → `spinWaitNs(MAB)` → `write(513b)` | 602–657 |
| `port.set({brk})` | Sí, modo alternativo `sendFrameSetBreak()` | 550–588 |
| Overlap detect | `_overlapCount`, `_overlapPeakMs` | 246–247 |
| Starvation detect | `_PHANTOM_STARVATION_MS = 40` | 243 |

**Observación crítica:** Este código está **100% funcional** pero **aislado**. La arquitectura WAVE 6012 decidió que `serialport` no puede vivir en `worker_threads` dentro de Electron (por contención de `bindings.node` en V8 Isolate). La solución correcta sería seguir usando `child_process.fork()` (que funciona), pero alimentarlo con SAB en lugar de IPC de datos.

### 2.2 `dmxPhantomWorker.ts` (WAVE 6010) — GHOST WORKER

**Archivo:** `src/hal/drivers/strategies/dmxPhantomWorker.ts`  
**Tipo de proceso:** `worker_threads` (`parentPort`, `workerData`)  
**Estado:** **No instanciado**. No hay `new Worker('./dmxPhantomWorker')` en ningún archivo del proyecto.

#### Payload Esperado
Este worker **SÍ espera `SharedArrayBuffer` vía `workerData.sab`**:

```ts
const sab = workerData?.sab as SharedArrayBuffer
const explicitPath = workerData?.portPath as string | undefined

if (!sab || !(sab instanceof SharedArrayBuffer)) {
  throw new Error('[DMX Phantom Worker] DMX_UNIVERSE_SAB no proporcionado o inválido.')
}

const reader = new DmxUniverseReader(sab)
```

**Compatibilidad con SAB:** **100%**. Es el único worker que ya está diseñado para leer del SAB. Sin embargo:

| Defecto | Detalle |
|---|---|
| **Sin BREAK** | `outputLoop()` hace `port.write(Buffer.from(frame.data.subarray(0, 512)))` directamente. Nunca genera BREAK ni MAB. |
| **Sin MAB** | No hay baudrate-switch, no hay `port.set({brk})`. |
| **Sin pacing** | `setImmediate(outputLoop)` corre tan rápido como el event loop lo permita (~44Hz sin control). |
| **Sin auto-detect en runtime** | Tiene `detectDmxPort()` pero nadie lo invoca desde el Main Process. |

**Conclusión:** Este archivo es un **placeholder arquitectónico**. La intención original era usar `worker_threads` para leer SAB, pero el bit-banging BREAK no fue implementado porque `serialport` en `worker_threads` dentro de Electron causa crashes (por el mismo motivo que `openDmxWorker.ts` usa `child_process`).

## TARGET 3: EL HUÉRFANO DE RED (ArtNetDriver.ts)

### 3.1 Arquitectura Interna

**Archivo:** `src/hal/drivers/ArtNetDriver.ts`  
**Clase:** `ArtNetDriver extends EventEmitter`  
**Socket:** `dgram.Socket` (UDP 6454)  
**Rate limiting:** `minSendInterval = 1000 / refreshRate` (default 44Hz = ~22.7ms)  
**Discovery:** ArtPoll periódico cada 2.5s  

#### Mecanismo de Tick / Loop Interno

**ArtNet NO tiene un loop interno propio.** No usa `setInterval` ni `setImmediate`. Es un driver **reactive / push-based**:

```ts
// Los métodos públicos de envío son llamados por el consumer externo:
send(): boolean                 // Envía universe config (legacy)
sendUniverse(universe: number): boolean   // Envía un universo específico
sendAll(): Promise<{ success; universesSent; errors }>  // Batch multi-universe
```

Cada método verifica rate limiting **síncrono** (`Date.now() - lastFrameTime < minSendInterval`) y descarta el frame si es demasiado pronto. El envío real es asíncrono (`socket.send(..., callback)`).

#### De Dónde Esperaba Leer los Universos (Pre-Aether)

Antes de Aether Glass, el flujo era:

```
TickEngine → HAL.sendUniverseRaw(universe, data) → USBDMXDriverAdapter
                                            ↓
                                     UniversalDMXDriver.setUniverse(universe, data)
                                            ↓
                                     (para ArtNet vía CompositeDMXDriver)
                                     ArtNetDriverAdapter.send(packet)
                                            ↓
                                     ArtNetDriver.setBuffer(buffer, universe)
                                            ↓
                                     ArtNetDriver.sendUniverse(universe) // UDP
```

En este flujo, `ArtNetDriver` mantenía sus propios buffers internos:

```ts
private dmxBuffer: Buffer                          // Legacy universe 0
private universeBuffers: Map<number, Buffer>       // Multi-universe (WAVE 2020.2b)
```

Los datos llegaban vía:
- `setChannel(channel, value, universe)` — llamado por `FixtureMapper` en el pipeline legacy
- `setChannels(startChannel, values, universe)` — batch parcial
- `setBuffer(buffer, universe)` — copia completa de 512 bytes

#### Qué Le Falta para Apuntar al SAB

| Requisito | Estado Actual | Qué Falta |
|---|---|---|
| Lectura de SAB | ❌ No existe | Un `DmxUniverseReader` (o equivalente) que lea del `DMX_UNIVERSE_SAB` |
| Loop de cadencia | ❌ No existe | Un `setInterval` o `setImmediate` que llame `sendAll()` periódicamente |
| Detección de cambio | ❌ No existe | Comparación frame-a-frame para evitar enviar UDP idénticos (ahora el SAB siempre tiene un `frameId` nuevo) |
| Throttle por driver | ✅ Existe | `minSendInterval` ya está, pero nadie lo configura dinámicamente desde Aether |
| Multi-universe SAB | ❌ No existe | El SAB actual (`DmxSabHandlers.ts`) solo soporta un universo en su estructura (ver layout) |

**Análisis del SAB actual vs ArtNet multi-universe:**

```ts
// DmxSabHandlers.ts — Estructura actual:
// i32[0] = SEQLOCK
// i32[1] = frameId
// i32[2] = dirtyMask (64-bit split en 2 i32)
// u8[DMX_HEADER_BYTES ... DMX_HEADER_BYTES+DMX_DATA_BYTES] = datos universo
```

El SAB actual solo almacena **datos raw** para un universo (o un array de universos en `commitFrame` que se serializan en offsets contiguos). ArtNet necesita **hasta 32,768 universes** (spec Art-Net 4). El SAB actual no tiene offsets por universo; el `commitFrame` itera `uniList[universe]` y escribe en posiciones calculadas. ArtNet necesitaría leer esos offsets.

**Conclusión:** ArtNet está **completamente desconectado** del pipeline Aether. No lee del SAB, no tiene loop propio, y su `sendAll()` nunca es llamado con datos frescos del `NodeResolver`. Es un driver zombie: conectado a la red, enviando ArtPoll, pero sin payload DMX.
