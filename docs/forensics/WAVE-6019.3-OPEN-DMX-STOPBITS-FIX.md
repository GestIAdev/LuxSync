# WAVE 6019.3 — OpenDMXStrategy: STOP BITS Fix + Baud-Switch Callback Ordering

## Status
✅ **RESUELTO** — Fixtures encienden y mantienen estado estable. No parpadeos detectados tras 2+ minutos de operación continua.

---

## Symptom
Oscuridad total en fixtures DMX (OpenDMX USB / IMC UD 7S). Loop de output ejecutándose (logs `[SNIFFER]` confirmaban actividad), pero cero respuesta física. Previamente se habían observado "flashes aleatorios" con una implementación de baud-switch sin callback ordering.

---

## Forensic Timeline

### Phase 1: Loop execution verification
- Inyectados logs granulares `[SNIFFER]` en `runTick()` y `sendFrame()`.
- Descubierto bug: `runTick` retornaba temprano si `!port.isOpen` sin re-programar `setTimeout`, matando el bucle recursivo.
- Fix: todos los early-returns de `runTick` ahora programan retry con `setTimeout(..., 25)`.

### Phase 2: Native BREAK signaling ruled out
- Intentado `port.set({ brk: true/false })` con callbacks.
- Resultado: negro absoluto. Diagnóstico: `EscapeCommFunction(SETBREAK)` no está implementado en drivers CH340 / clones FTDI baratos. El callback devuelve éxito pero la línea TX nunca baja.

### Phase 3: Baud-switch with callback ordering
- Revertido a baud-rate switching (WAVE 4942 approach): `76923 baud` → byte `0x00` → `250000 baud`.
- Implementado callback ordering: `port.update(BREAK_BAUD)` → callback → `port.write([0x00], callback)` → `spinWaitNs` → `port.update(DMX_BAUD)` → callback → payload.
- Resultado: seguía sin luces. Race condition entre `write()` y `update()` solucionada, pero persistía el negro.

### Phase 4: Payload content diagnostics
- Agregado `logPayload()` para verificar contenido de `dmxBuffer` cada 1s.
- Resultado: `nonZero=4/513` — el buffer tenía datos (modo manual L2), pero los canales 1-5 mostraban ceros, indicando que los fixtures no estaban en los primeros canales.

### Phase 5: The Smoking Gun — STOP BITS
- Revisado constructor `SerialPort`: por defecto usa `stopBits: 1`.
- **DMX512 requiere `stopBits: 2`** (EIA-485 + UART config).
- Fix aplicado: `new SerialPort({ ..., dataBits: 8, stopBits: 2, parity: 'none' })`.
- **Resultado inmediato**: fixtures encendieron al 50% dimmer, azul, modo manual L2.

---

## Root Cause
```
SerialPort default:  { dataBits: 8, stopBits: 1, parity: 'none' }
DMX512 requirement:  { dataBits: 8, stopBits: 2, parity: 'none' }
                                    ^^^^^^^^^^^
                                    MISSING
```
Con `stopBits: 1`, los fixtures DMX interpretaban el frame como corrupto y lo descartaban. Dependiendo del estado interno del UART del fixture, esto producía:
- Flashes aleatorios (intentos fallidos de sincronización) en versiones sin callback ordering.
- Negro absoluto (fixture da up y mantiene last-looks) en versiones con callback ordering.

---

## Files Modified
- `src/hal/drivers/strategies/OpenDMXStrategy.ts`
  - `connect()`: agregado `dataBits: 8, stopBits: 2, parity: 'none'` al constructor SerialPort.
  - `sendFrame()`: `port.write([0x00])` ahora tiene callback antes de `spinWaitNs` + `port.update(DMX_BAUD)`.
  - `runTick()`: early-returns ahora reintentan con `setTimeout` en vez de matar el bucle.
  - Agregados helpers `sniff()` (throttle 1Hz) y `logPayload()` (diagnóstico de contenido).

---

## Verification
- `[SNIFFER] PAYLOAD DIAG: nonZero=4/513` — buffer contiene datos manuales L2.
- Fixtures encienden y mantienen estado sin parpadeos tras 2+ minutos.
- Output disabled global (`_outputEnabled=false`) pero L2 manual overrides bypasean el gate — comportamiento intencional.

---
