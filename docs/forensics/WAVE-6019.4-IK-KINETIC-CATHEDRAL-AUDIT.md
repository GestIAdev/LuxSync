## Resumen Ejecutivo

Se identificaron **dos síntomas separados** con **causas raíz distintas** que comparten un denominador común: la arquitectura Aether Glass cambió el flujo de datos de la UI al backend, y ciertos guards/pipelines del modo espacial (IK) y clásico (VMM) quedaron rotos o inconsistentes tras la migración.

| Síntoma | Ruta Afectada | Severidad |
|---|---|---|
| Modo clásico: desincronización + intento de apuntar al techo tras unlock | `KineticAdapter` → `NodeArbiter` → `NodeResolver` | 🔴 Alta |
| Modo espacial: "descuelgue" al cambiar patrón / unlock | `applySpatialTarget` → `AetherKineticEngine` → `NodeArbiter` | 🔴 Alta |
| Hold interpretado como idle/reposo | `AetherIPCHandlers` → `NodeArbiter._applyRelativeOffsetFusion` | 🟡 Media |

## 1. Modo Clásico — Desincronización + Techo en Ceiling Mount

### 1.1 Síntoma Observable
Al hacer **unlock** en la KineticsCathedral:
- Los 6 movers intentan dibujar en el techo (clamp evita el impacto físico).
- Los focos centrales del rectángulo (2 a cada lado del eje X=0) se desincronizan.
- Se pierde la semiesfera inferior de dibujo que debería apuntar al suelo (ceiling mount).

### 1.2 Análisis Causa Raíz — DUAL FACTOR

#### Factor A: Clasificación Left/Right inconsistente en focos centrales
**Archivo:** `src/core/aether/adapters/KineticAdapter.ts:243`

```typescript
const lrPhaseOffset = (node.zoneId && typeof node.zoneId === 'string' && node.zoneId.includes('right')) ? Math.PI : 0
```

- Los 6 movers están divididos en 3 left + 3 right.
- Los 2 focos más cercanos a X=0 (uno pertenece a left, otro a right) reciben fases opuestas (`0` vs `π`).
- En patrones simétricos (circle, eight), esto causa **movimiento en espejo** en vez de convergencia.
- El foco central "right" se desfasa π radianes respecto al central "left", rompiendo el patrón global.

#### Factor B: `node.ikOrientation` undefined → VMM aplica offset de FLOOR en fixture CEILING
**Archivos:**
- `src/engine/movement/VibeMovementManager.ts:1052-1069`
- `src/core/aether/resolver/NodeResolver.ts:1076-1078`
- `src/core/aether/resolver/NodeResolver.ts:1302-1318`

**Flujo del bug:**

1. **VMM `generateIntent`** lee `mountOrientation = node.ikOrientation?.installation`.
2. Si `node.ikOrientation` es `undefined` (regresión o edge case en la hidratación del nodo), `mountOrientation` cae a `undefined`.
3. VMM aplica `tiltOffset = TILT_OFFSET_BY_VIBE[vibeId]` (ej. `-0.35` para techno) — **offset de floor**.
4. VMM ejecuta el clamp de floor: `position.y = Math.min(position.y, TILT_CEILING)` — permite valores **positivos**.
5. El KineticAdapter emite `tilt_offset = clamp(intent.y, -1, 1)`. Si `intent.y` es positivo, el offset empuja el tilt hacia arriba.
6. **NodeResolver** detecta ceiling mount por `device.orientation` (del fixture JSON) y ejecuta:
   ```typescript
   if (invertClassicKineticAxes) {
     dmxValue = sanitizeDmxByte(255 - dmxValue)
   }
   ```
7. **Efecto combinado:** offset de floor (positivo) + inversión ceiling = haz apunta al **techo** en vez del suelo.

**Nota histórica:** WAVE 4932 fixeó exactamente este problema inyectando `ikOrientation` en `NodeExtractionPipeline._buildKineticNode`. Sin embargo, la auditoría detecta que el fix depende de que `orientation` venga del `ShowFileV2` (`fv2.orientation ?? installationType ?? physics?.orientation`). Si cualquiera de estas fuentes es `undefined` o no está hidratada correctamente en Aether Glass, `node.ikOrientation` sigue siendo `undefined`.

## 2. Modo Espacial — "Descuelgue" al Cambiar Patrón / Unlock

### 2.1 Síntoma Observable
- Operador setea radar espacial (IK 3D). Los fixtures apuntan al target.
- Al cambiar patrón manualmente desde la UI (botones de la Cathedral) o al hacer unlock, los movers "descuelgan" y vuelven a reposo (centro neutro).
- Hay que volver a setear el radar espacial y repetir todo el proceso.

### 2.2 Análisis Causa Raíz — Ruta IK Muerta en NodeResolver

**Archivos:**
- `src/core/aether/adapters/KineticAdapter.ts:193-195`
- `src/core/aether/resolver/NodeResolver.ts:978-980`
- `src/core/aether/AetherIPCHandlers.ts:680-860`

**Flujo del bug:**

1. `KineticAdapter.process()` **limpia explícitamente** los canales espaciales cada frame:
   ```typescript
   this._valuesDict['targetX'] = undefined as any
   this._valuesDict['targetY'] = undefined as any
   this._valuesDict['targetZ'] = undefined as any
   ```
2. `NodeResolver` decide ruta IK vs clásica por:
   ```typescript
   const hasSpatialTarget = channelValues[CH_TARGET_X] !== undefined
   if (!kineticNode.isContinuous && hasSpatialTarget) {
     this._writeNodeIK(...)   // ← RUTA ESPACIAL
     return
   }
   ```
3. Como `targetX` nunca está definido en el `arbitratedNodeMap`, `hasSpatialTarget` es **siempre `false`**.
4. **Resultado:** `_writeNodeIK` **nunca se ejecuta** en el pipeline actual. La ruta IK en `NodeResolver` está **muerta**.

5. El modo espacial funciona puramente como **L2 bypass**:
   - `KineticsBridge._flushSpatial` → `applySpatialTarget` IPC
   - `applySpatialTarget` resuelve IK y escribe `pan_base`/`tilt_base` en **`_motorKineticOverrides`** (L2-MOTOR).
   - `NodeArbiter._applyRelativeOffsetFusion` lee `_motorKineticOverrides` y aplica a `_result`.

6. Cuando el operador **cambia de patrón** o hace **unlock**:
   - `AetherIPCHandlers.setManualPattern` con `pattern === 'hold'` → llama a `aetherKineticEngine.removeNodes(...)`.
   - `removeNodes` ejecuta `arbiter.clearMotorKineticOverride(nodeId)`.
   - `_motorKineticOverrides` pierde el `pan_base`/`tilt_base` del target espacial.
   - `_manualOverrides` también se limpia si no hay `anchorPan`/`anchorTilt` (WAVE 4937.1).
   - Sin base ni patrón, `_applyRelativeOffsetFusion` cae al fallback `0.5` (centro neutro).
   - Los fixtures "descuelgan" al reposo.

**Conclusión:** El modo espacial no está realmente integrado en el pipeline de intenciones L0. Es un hack de L2 que se rompe tan pronto como el motor L2 se detiene.

## 3. Hold Interpretado como Idle/Reposo

### 3.1 Síntoma Observable
El backend interpreta el cambio de patrón o unlock como "hold", pero los fixtures vuelven al centro neutro en vez de congelarse en su última posición.

### 3.2 Análisis Causa Raíz — Hold Detection vs Clear Manual Override

**Archivos:**
- `src/core/aether/AetherIPCHandlers.ts:422-442`
- `src/core/aether/NodeArbiter.ts:837-852`

**Flujo del bug:**

1. En el IPC handler, `pattern === null|'static'|'hold'` dispara:
   ```typescript
   aetherKineticEngine.removeNodes(removeNodeIds, arbiter)
   if (anchorPan === undefined && anchorTilt === undefined) {
     for (const id of fixtureIds) {
       arbiter.clearManualOverride(`${id}:kinetic`)
     }
   }
   ```
2. `clearManualOverride` elimina el override del NodeArbiter. **Pero** la intención del diseño (WAVE 4934) era que HOLD = congelar en el ancla del radar.
3. `NodeArbiter._applyRelativeOffsetFusion` detecta hold así:
   ```typescript
   const isHoldState = (hasManualPan || hasManualTilt) && !hasMotorPan && !hasMotorTilt
   if (isHoldState) {
     record['pan'] = manualPan as number
     record['tilt'] = manualTilt as number
     continue
   }
   ```
4. **Problema:** `isHoldState` requiere que `_manualOverrides` **todavía** tenga `pan_base`/`tilt_base`. Pero `clearManualOverride` lo acaba de borrar.
5. Sin `_manualOverrides` y sin `_motorKineticOverrides`, la condición `!hasBasePan && !hasBaseTilt && !hasPanOffset && !hasTiltOffset` hace `continue` (skip del nodo).
6. El nodo no genera output cinético. El fixture cae a **defaults del fixture JSON** o a **reposo** (lo que el visualizador interprete como idle).

**Nota:** El diseño original de "HOLD" como estado de congelación se rompió en WAVE 4937.1 cuando se agregó `clearManualOverride` en el flujo de unlock. Antes, el ancla del radar persistía en `_manualOverrides` y `isHoldState` funcionaba.

## 4. Interacción Crítica: Aether Glass + UI Data Flow

La arquitectura Aether Glass introdujo un desacoplamiento entre la UI y el backend:
- **Antes:** La UI escribía directamente en `masterArbiter` y `vibeMovementManager`.
- **Ahora:** La UI envía comandos por IPC → `AetherIPCHandlers` → `AetherKineticEngine` / `NodeArbiter`.

Esto rompió dos supuestos del pipeline original:
1. **Supuesto roto:** `KineticAdapter` siempre emitiría `targetX`/`targetY`/`targetZ` en modo espacial. **Realidad:** Ahora emite `pan_offset`/`tilt_offset` y limpia los targets.
2. **Supuesto roto:** `_manualOverrides` persistiría el ancla del radar tras unlock. **Realidad:** `clearManualOverride` la limpia explícitamente para evitar "Ghost Anchors".

La UI sigue siendo WYGIWYS, pero el backend no mantiene el estado que la UI espera.

## 5. Recomendaciones de Fix (Sin Implementar)

### Fix A: Revivir la ruta IK en NodeResolver (Modo Espacial) → REPLANTEADO COMO FIX A'
**Original:** Hacer que `applySpatialTarget` escriba `targetX`/`targetY`/`targetZ` o cambiar el gatekeeper.

**Fix A' aplicado (Hidratación):** La causa raíz del descuelgue en modo clásico era que `_buildForgeGroupNode` (ruta Forge Graph) no hidrataba `ikOrientation` en los nodos KINETIC, a diferencia de `_buildKineticNode` (ruta legacy) que sí lo hacía.

**Implementado en:** `src/core/aether/ingestion/NodeExtractionPipeline.ts`
- `_buildNodesFromForgeGraph` ahora recibe y propaga `orientation` (línea 539)
- `_buildForgeGroupNode` ahora recibe `orientation` y lo inyecta como `ikOrientation` en la rama KINETIC (líneas 758-766)
- `extract()` pasa `resolvedOrientation` a ambas rutas (Forge y legacy) por igual (línea 395)

**Resultado:** `node.ikOrientation.installation` ahora siempre está poblado, eliminando la necesidad del fallback defensivo del Fix B para fixtures con Forge Graph.

### Fix B: Inyectar `ikOrientation` en todos los nodos KINETIC ✅ COMPLETADO (vía Fix A')
**Mitigación defensiva aplicada en:** 
- `src/engine/movement/VibeMovementManager.ts:1053-1062` — `generateIntent` normaliza `mountOrientation` a lowercase con fallback `'floor'`.
- `src/core/aether/adapters/KineticAdapter.ts:273-287` — documentado el riesgo.

**Causa raíz resuelta por Fix A':** `NodeExtractionPipeline._buildForgeGroupNode` ahora hidrata `ikOrientation` correctamente. El fallback defensivo del VMM sigue siendo valioso como safety net.

### Fix C: Hold State Preservation ✅ APLICADO
En `AetherIPCHandlers.setManualPattern`, cuando `pattern === 'hold'`, en vez de limpiar `_manualOverrides`, **migrar** el último `pan_base`/`tilt_base` del motor a `_manualOverrides` antes de llamar `removeNodes`. Así `isHoldState` tiene datos para congelar.

**Implementado en:** `src/core/aether/AetherIPCHandlers.ts:425-458`
- Itera `removeNodeIds`, lee `arbiter.getMotorKineticOverride(nodeId)`.
- Si el motor tiene `pan_base`/`tilt_base` (IK spatial target activo), los inyecta en `_manualOverrides` vía `setManualOverride`.
- Flag `motorStateMigrated` evita que `clearManualOverride` borre el estado recién migrado.
- `NodeArbiter._applyRelativeOffsetFusion` ahora detecta `isHoldState` correctamente y congela en la última posición IK.

### Fix D: Clasificación L/R Determinista para Focos Centrales ✅ APLICADO
En `KineticAdapter` o en la hidratación del stage, definir una regla explícita para focos en X≈0: si `|x| < epsilon`, forzar `zoneId = 'center'` y asignar `lrPhaseOffset = 0` (o una fase intermedia) para evitar el salto de π entre left y right.

**Implementado en:** `src/core/aether/adapters/KineticAdapter.ts:238-257`
- Lee `node.physicalPosition.x` (o `node.position.x` como fallback).
- Zona neutral de ±0.5m alrededor de X=0: focos en `[-0.5, 0.5]` reciben fase 0.
- `x > 0.5` → `Math.PI` (derecha); `x < -0.5` → `0` (izquierda).
- Fallback a `zoneId.includes('right')` si no hay posición física (compat legacy).
