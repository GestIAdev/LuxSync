# WAVE 6019.6 — Forensic Audit: Release vs Hold Handoff

## Estado
**FIX APLICADO** en `KineticsBridge.ts:77` — `toEnginePattern('none')` ahora retorna `'hold'` en lugar de `'release'`.

## Diagnóstico Forense

### Síntoma reportado
> "El motor espacial sigue haciendo release cuando suelto un boton de patron manual y con los dos focos centrales a su bola. La velocidad si se ha solcionado, pero siguen mostrando independencia, lag y patron que intenta irse al techo."

### Causa Raíz Identificada

**Problema: `toEnginePattern('none')` retornaba `'release'`**

En `KineticsBridge.ts:76-80`, la función de mapeo de UI pattern a engine pattern tenía:

```typescript
function toEnginePattern(p: string): string {
  if (p === 'none') return 'release'   // ← BUG
  if (p === 'static') return 'hold'
  return p
}
```

Cuando el usuario deselecciona un patrón manual (clic en patrón activo), `PatternArsenal.tsx:49` envía `'none'` → `movementStore.setActivePattern('none')` → `KineticsBridge` suscripción → `_flushPattern` envía `enginePattern = 'release'`.

**Diferencia crítica entre `'release'` y `'hold'` en el backend:**

| Acción UI | Pattern enviado | Backend (`AetherIPCHandlers.ts`) | Efecto en L2 |
|-----------|----------------|----------------------------------|--------------|
| Deseleccionar patrón | `'release'` (antes) | Línea 430: purga destructiva pura. Limpia `_manualOverrides`, remueve nodos del engine, silencia VMM. | L2 vacío → L0 toma control inmediatamente. |
| Deseleccionar patrón | `'hold'` (ahora) | Línea 445: freeze intencional. Migra estado motor a `_manualOverrides`, remueve nodos, silencia VMM. | L2 congela posición actual. L0 silenciado. |
| Botón UNLOCK | `null` | Línea 430: misma purga destructiva. | L2 vacío → L0 toma control. |

### Por qué esto causaba todos los síntomas

1. **"Independencia" (focos a su bola)**: Al enviar `'release'`, L2 se purga completamente. `KineticAdapter` (L0) retoma control y genera offsets por fixture con desfases de fase individuales (`lrPhaseOffset`, `chaosPhase`). Cada foco se mueve independientemente en lugar de mantener su posición congelada.

2. **"Lag"**: La purga destructiva elimina tanto el estado del motor como los manual overrides. La transición es abrupta (no hay release fade de snapshot porque `clearManualOverride` encuentra overrides ya vacíos). El salto brusco se percibe como lag.

3. **"Patrón que intenta irse al techo"**: Al retomar L0, `VibeMovementManager.generateIntent()` arranca desde `phase = 0` (fix previo de scheduler reset). Para fixtures ceiling-mounted, los offsets iniciales del VMM pueden calcularse con base en 0.5 (default) en lugar del target IK real, y tras la inversión de ejes del `NodeResolver`, el haz apunta hacia arriba.

### Arquitectura de Handoff

```
UI Pattern Arsenal → activePattern = 'none'
                     ↓
              KineticsBridge.toEnginePattern('none')
                     ↓
            ┌─────────────────────┬─────────────────────┐
            │   ANTES (BUG)       │   DESPUÉS (FIX)     │
            │   'release'           │   'hold'            │
            └─────────────────────┴─────────────────────┘
                     ↓                        ↓
       AetherIPCHandlers:430          AetherIPCHandlers:445
       Purga destructiva              Freeze (migra motor→manual)
                     ↓                        ↓
            L2 vacío, L0 activo        L2 congelado, L0 silenciado
```

### Preservación del UNLOCK

El botón **UNLOCK** (`KineticsCathedral.tsx:141`) **NO** usa el bridge. Envía `pattern: null` directamente via IPC (`lux:aether:setManualPattern`), bypassando completamente `toEnginePattern`. Esto garantiza que:
- Deseleccionar patrón = freeze (`'hold'`)
- UNLOCK = liberación destructiva real (`null` → `'release'` en backend)

## Segundo Fix — targetX/Y/Z Residuales (Spatial → Classic Corruption)

### Síntoma residual reportado
> "En el momento que manipulo el motor espacial, luego se corrompe el clásico también."

### Causa Raíz Identificada

Cuando el usuario manipula el motor espacial:
1. `SpatialTargetPad` → `programmerStore.setSpatialPosition(target)` → `fixtureOverrides` guarda `targetX/Y/Z`
2. `ProgrammerAetherBridge` lee `fixtureOverrides` y envía `targetX/Y/Z` como manual overrides al backend (`setManualOverrides`)
3. Backend: `_manualOverrides` recibe `targetX/Y/Z`

Cuando el usuario luego selecciona un patrón clásico o deselecciona patrón:
1. `KineticsBridge._flushPattern` envía `setManualPattern('wave')` o `'hold'`
2. PERO NUNCA limpia `targetX/Y/Z` del `programmerStore`
3. `ProgrammerAetherBridge` **sigue** enviando `targetX/Y/Z` residuales en el siguiente frame
4. Backend: `_manualOverrides` tiene `targetX/Y/Z` → `KineticAdapter.hasSpatialTarget = true` → **L0 silenciado**
5. Alternativamente: `NodeResolver` ve `targetX` en `channelValues` → toma ruta IK con target espacial viejo → fixtures apuntan a posición estática incorrecta

### Fix Aplicado

**Archivo:** `electron-app/src/stores/programmerStore.ts`

```typescript
// NUEVO método en interfaz + implementación:
clearSpatialTargets: (fixtureIds: string[]) => void

// Implementación (línea ~892):
clearSpatialTargets: (fixtureIds) => {
  set(state => {
    const next = new Map(state.fixtureOverrides)
    for (const id of fixtureIds) {
      const ov = next.get(id)
      if (ov) next.set(id, {
        ...ov,
        targetX: null,
        targetY: null,
        targetZ: null,
      })
    }
    const dirty = new Set(state.dirtyFamilies)
    dirty.add('KINETIC')
    return { fixtureOverrides: next, dirtyFamilies: dirty }
  })
},
```

**Archivo:** `electron-app/src/bridges/KineticsBridge.ts:549`

```typescript
// Dentro de _flushPattern, ANTES de enviar setManualPattern:
useProgrammerStore.getState().clearSpatialTargets(fixtureIds)
```

### Impacto del Fix

- Al salir del modo espacial (seleccionar patrón clásico o deseleccionar → hold), `targetX/Y/Z` se limpian del store inmediatamente
- `ProgrammerAetherBridge` deja de enviarlos en el siguiente frame
- Backend: `_manualOverrides` solo recibe lo que el patrón/clásico necesita
- `KineticAdapter` ya no ve `targetX` en manual → genera offsets L0 normalmente
- `NodeResolver` no ve `targetX` en `channelValues` → usa flujo clásico (pan/tilt)

## Tercer Fix — Cortafuegos IK (Snapshot Poisoning en Release Fader)

### Síntoma reportado
> "Espacial manda los 6 movers (left y right) al techo (no pasan por el clamp), y el clasico, solo los centrales."

### Diagnóstico: Snapshot Poisoning

Cuando se hace Unlock desde el radar espacial, `clearManualOverride` en `NodeArbiter.ts` toma un snapshot de TODOS los canales en `_manualOverrides` para el Release Fader. Entre ellos, `targetX`, `targetY`, `targetZ` — coordenadas 3D del IK.

El Release Fader interpola estas coordenadas hacia 0 durante ~1-2 segundos. El `NodeResolver` ve `targetX` en `channelValues` (aunque esté decayendo) y **mantiene la ruta IK activa** en lugar de soltarla. Al interpolar XYZ hacia (0,0,0), el motor espacial apunta los focos al centro/techo. Los centrales, al cruzar X=0, sufren singularidad trigonométrica y se desincronizan.

### Fix Aplicado

**Archivo:** `electron-app/src/core/aether/NodeArbiter.ts`

1. **Constante `IK_POISON_KEYS`** (línea 115):
```typescript
const IK_POISON_KEYS = new Set(['targetX', 'targetY', 'targetZ', 'focusX', 'focusY', 'focusZ'])
```

2. **Cortafuegos en `clearManualOverride`** (línea 376):
```typescript
for (const key in channels) {
  if (IK_POISON_KEYS.has(key)) continue  // ← CORTAFUEGOS
  // ... snapshot normal ...
}
```

3. **Corrección de `SLOW_RELEASE_CHANNELS`** (línea 391):
   `SLOW_RELEASE_CHANNELS.has(key)` → `SLOW_RELEASE_CHANNELS.has(snapshotKey)` para que `pan_base→pan` y `tilt_base→tilt` hereden `RELEASE_MS_SLOW` (1000ms) correctamente.

### Impacto

- Al hacer Unlock/Release desde modo espacial, `targetX/Y/Z` se purgan inmediatamente sin pasar por el Release Fader
- `NodeResolver` deja de ver coordenadas IK → suelta la ruta espacial y usa ángulos clásicos
- Los 6 movers ya no colapsan al techo durante el fade
- Los centrales ya no cruzan la singularidad X=0
