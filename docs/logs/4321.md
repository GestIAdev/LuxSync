Hallazgo alternativo — posible causa real del salto
El bug que describes (fixtures saltan a posición anterior) no viene del drag → store → flush, sino de un desfase de sincronización en cambio de selección:

KineticsBridge.ts:327-356
private async _hydrateFromBackend(fixtureIds: string[]): Promise<void> {
  ...
  hydration.setNodeStates(states, fixtureIds)
}
_hydrateFromBackend (llamado en cada cambio de selección) hidrata solo kineticHydrationStore, pero nunca actualiza movementStore.pan/tilt.

Escenario del bug:

Seleccionas fixture A → _hydrateFromBackend lee backend (pan=270, tilt=135) → pone en kineticHydrationStore
Mueves radar a (pan=400, tilt=200) → movementStore y kineticHydrationStore se sincronizan ✅
Cambias selección a fixture B → _hydrateFromBackend lee backend (pan=100, tilt=50) → pone en kineticHydrationStore
NO actualiza movementStore → movementStore.pan sigue siendo 400
Mueves radar un poquito → handlePanTiltChange actualiza movementStore a (pan=405, tilt=205) ✅
Pulsas patrón → _flushPattern lee movementStore.pan=405 → envía anchor 405
Pero fixture B en backend está en pan=100... y el patrón parte desde 405 = salto brusco
Esto no es "posición anterior del radar", es "última posición del radar del fixture A anteriormente seleccionado" que quedó stale en movementStore tras el cambio de selección.
