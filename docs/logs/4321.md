# WAVE 4911 — THE Z-AXIS DIVERGENCE: Reporte Forense Pre-Diagnóstico

Fecha: 2026-05-18

## RESUMEN EJECUTIVO

El eje X converge perfectamente. El tilt (Y) es perfecto. El eje Z diverge en todos los fixtures sin excepción. La causa raíz **no es la orientación de montaje** — es una incompatibilidad de signo en la componente Z entre la fórmula `atan2(local.x, local.z)` del IK y la fórmula `heading_z = -cos(panAngle)` del visualizador. La solución es una sola línea: cambiar `atan2(local.x, local.z)` a `atan2(local.x, -local.z)` en el IK, sin tocar nada más.

---

## 1. Geometría del Visualizador (confirmada por código fuente)

```

PAN_AXIS                = [0, 1, 0]  → rotación sobre eje Y mundo
TILT_AXIS               = [1, 0, 0]  → rotación sobre eje X
Yoke brazos             = x=±0.10, z=0  → eje de oscilación del tilt = X
                                          "frente" natural del yoke = ±Z
Haz emite en            = -Y local del headRef (suelo directo cuando tilt=0.5)
panAngle (línea 298)    = -(smoothPan - 0.5) × mechanicalPanRangeRad   ← CON negativo

TILT_REST_ANGLE         = 0 (ceiling: DMX center apunta al suelo)
```

## 2. Derivación del Heading Real del Haz

Con la fórmula de pan del visualizador `panAngle = -(pan - 0.5) * range`, la proyección horizontal del haz en XZ es:

```
heading_x = -sin(panAngle) =  sin((pan - 0.5) * range)
heading_z = -cos(panAngle) = -cos((pan - 0.5) * range)
```

Sustituyendo `pan = (panDeg + range/2) / range` → `(pan - 0.5) = panDeg / range`:

```
heading_x =  sin(panDeg_rad)
heading_z = -cos(panDeg_rad)
```

Y el IK calcula `panDeg = atan2(local.x, local.z)` donde con `pitch=0, yaw=0` → `local.z = dz`:

```
sin(atan2(dx, dz)) =  dx / |d_xz|   →  heading_x tiene mismo signo que dx  ✓  (X converge)
cos(atan2(dx, dz)) =  dz / |d_xz|   →  heading_z = -dz / |d_xz|            ✗  (Z diverge)
```

**Heading_z tiene signo OPUESTO a dz en todos los casos.** Esto explica exactamente el síntoma:
los fixtures delanteros (dz > 0) apuntan hacia -Z y los traseros (dz < 0) apuntan hacia +Z.

## 4. Análisis de la Hipótesis: pitch=180 en MOUNT_ANGLES.ceiling

**Efecto matricial de `pitch=180` en `rotateToLocalFrame`:**
Con `-pitchRad = -π`: `cos(-π) = -1`, `sin(-π) = 0`

```
y2 = y1 * (-1) - z1 * 0 = -dy    → local.y = -dy  (se invierte)
z2 = y1 * 0   + z1 * (-1) = -dz  → local.z = -dz  (se invierte)
```

Resultado para el pan:
- `panDeg = atan2(dx, -dz)` → **heading_z = -cos(atan2(dx,-dz)) = dz/|d|** ✓ (Z converge)
- `heading_x = sin(atan2(dx,-dz)) = dx/|d|` ✓ (X sigue convergiendo)

Resultado para el tilt:
- `local.y = -dy`. Con `dy < 0` (target abajo del fixture ceiling), `local.y = +|dy| > 0`
- Fórmula actual: `tiltDeg = atan2(horizontalDist, -local.y) = atan2(horizontalDist, -|dy|)`
  → ángulo en segundo cuadrante (>90°) → tiltDMX fuera de rango → **TILT DESTRUIDO** ✗

**Veredicto hipótesis pitch=180: parcialmente correcta en Z, pero mata el tilt.**

---

## 5. Compensación Exacta del Tilt si se Aplica pitch=180

Si se usa `pitch=180` (local.y = -dy), para mantener el tilt actual idéntico:

```
Antes:  tiltDeg = atan2(horizontalDist, -local.y)  donde local.y = dy
Después: local.y = -dy → tiltDeg = atan2(horizontalDist, -(-dy)) = atan2(horizontalDist, dy)
```

La compensación es **quitar el signo negativo** en la fórmula de tilt:
```typescript
// CON pitch:180 activo en MOUNT_ANGLES.ceiling:
const tiltDeg = Math.atan2(horizontalDist, local.y) * RAD_TO_DEG  // sin el negativo
```

El resultado matemático final es idéntico al actual.

---

## 6. Alternativa Quirúrgica — La Solución Limpia

En vez de modificar MOUNT_ANGLES (que afecta la matriz completa y crea acoplamiento entre Y y Z), la corrección mínima es invertir solo `local.z` en el argumento de `atan2` del pan:

### Código actual (IK — InverseKinematicsEngine.ts, línea ~245):
```typescript
panDeg = Math.atan2(local.x, local.z) * RAD_TO_DEG
```

### Propuesta WAVE 4911:
```typescript
panDeg = Math.atan2(local.x, -local.z) * RAD_TO_DEG
```

**Prueba algebraica:**
```
panDeg = atan2(dx, -dz)
heading_x = sin(atan2(dx,-dz)) = dx/|d|   → mismo signo que dx  ✓  (X sigue convergiendo)
heading_z =-cos(atan2(dx,-dz)) = dz/|d|   → mismo signo que dz  ✓  (Z converge)
```

El tilt NO se toca. El MOUNT_ANGLES NO se toca. El INVARIANTE de WAVE 4899 (tiltDeg con -local.y) NO se toca. La función `rotateToLocalFrame` NO se toca.

# WAVE 4910 - Reporte Ejecutivo (histórico)

## 1. Diagnostico Completo

El problema visible fue anti-convergencia perfecta en Spatial IK: el aspa de 6 beams abria hacia afuera en vez de colapsar al centro.

Hallazgo clave:
- WAVE 4905 forzo `panInvert=true` por orientacion ceiling en el flujo de `applySpatialTarget`.
- Ese cambio partio de una formula de visualizacion asumida con signo negativo.
- La formula real del visualizador no tiene ese negativo, por lo que el signo final de pan quedo invertido respecto al objetivo.

Formula real en visualizador:
- En [electron-app/src/components/hyperion/views/visualizer/fixtures/HyperionMovingHead3D.tsx](electron-app/src/components/hyperion/views/visualizer/fixtures/HyperionMovingHead3D.tsx#L242):

```ts
const panAngle = (smoothPan.current! - 0.5) * PAN_RANGE
```

Consecuencia matematica con esa formula real:
- `panInvert=false` -> panDMX aprox 161 -> panAngle positivo -> convergencia.
- `panInvert=true`  -> panDMX aprox 94  -> panAngle negativo -> divergencia.

Veredicto:
- El bug no estaba en la trigonometria base del IK.
- El bug fue una inversion de pan aplicada con criterio equivocado (WAVE 4905).

## 2. Mapa Del Desastre

Cadena de fallo (de punta a punta):

1. IPC `applySpatialTarget` construia perfil IK con `panInvert=true` por ceiling.
2. IK devolvia pan invertido para los fixtures del abanico.
3. NodeArbiter pasaba `pan_base/tilt_base` correctamente a ruta clasica KINETIC.
4. NodeResolver no re-invertia PAN (solo aplica inversion clasica de orientacion sobre TILT).
5. El frontend consumia PAN ya invertido y lo convertia a angulo con formula sin signo negativo.
6. Resultado neto: direccion de giro opuesta al target en escena (aspa abierta).

Factores que enmascaraban el diagnostico:
- Comentarios historicos con formula vieja del visualizador.
- Coexistencia de rutas IK (`target_x/y/z`) y ruta clasica (`pan/tilt`) para KINETIC.
- Valor de `panInvert` del showfile en `false`, pero bypass en WAVE 4905 dentro del handler IPC.

## 3. Solucion Aplicada Por El Ejecutor

Se aplicaron 2 cambios concretos:

1. Revert de WAVE 4905 en el perfil IK de `applySpatialTarget`.
- Archivo: [electron-app/src/core/aether/AetherIPCHandlers.ts](electron-app/src/core/aether/AetherIPCHandlers.ts)
