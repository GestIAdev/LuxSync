## Executive Summary
**The L3 color intent IS correctly constructed by the effect and correctly handled by the Arbiter's L3 Supremacy mechanism. The color is lost during ZONE RESOLUTION in `HephaestusRuntime`, BEFORE any intent reaches the Arbiter.**

The `all-movers` composite zone is defined as `['movers-left', 'movers-right']` (type-based zoning). If the movers in the show file are assigned to **spatial zones** (e.g., `front-left`, `front-right`, `back-left`, `back-right`) instead of **fixture-type zones**, `all-movers` resolves to an empty fixture set. No outputs are generated for those fixtures. L0/L1 continues to paint them with the base palette (red), which is exactly what the user observes.

## 2. Why Other Zones Work

The `back` and `front` tracks in `corazon_latino.lfx` use spatial zones:
```json
{ "zones": ["back"] }
{ "zones": ["front"] }
```

These match fixtures whose `.zone` is literally `'back'` or `'front'`. PARs and washes are typically zoned by physical location, so these resolve correctly and emit outputs.

## 3. Zone Taxonomy Mismatch — The Root Cause

The system has **two coexisting zone taxonomies** that are not bridged:

| Taxonomy | Zones | Used by |
|----------|-------|---------|
| **Spatial** | `front`, `back`, `front-left`, `front-right`, `back-left`, `back-right`, `floor` | ColorSystem, LiquidAetherAdapter, most show files |
| **Fixture-Type** | `movers`, `movers-left`, `movers-right`, `pars`, `all-pars`, `all-movers` | `ZoneMapper` composites, `ZoneNodeRouter` composites |

`all-movers` is a **fixture-type composite**. It assumes movers are tagged by type. If the show file tags movers by their **spatial position** instead, the composite fails.

`ZoneNodeRouter` also builds `all-movers` from `movers + movers-left + movers-right`:
```
@src/core/aether/adapters/helpers/zone-node-router.ts:278-312
// Alias compuesto: all-movers = union determinista movers + movers-left + movers-right.
```

So even the Aether Matrix's `ZoneNodeRouter` (used by `SeleneAetherAdapter`) cannot find spatially-zoned movers under `all-movers`.

## 4. Arbiter L3 Logic — Not the Culprit

`NodeArbiter` handles L3 (`hephaestus` layer) correctly:

- `_primeL3DominancePrePass()` registers L3 channels before L0/L1 runs.
- `_applyIntent('hephaestus')` calls `_registerL3Dominance()` per channel.
- `_l3DominatedChannels` blocks L0/L1 on those exact channels.
- For Hephaestus color, `_l3HephColorNodeIds` also blocks L0 completely on those nodes.
- `MANUAL_HARD_LOCK` does NOT exclude color channels (`r`, `g`, `b`), but that only matters if there are active manual overrides.

**The L3 Supremacy mechanism is sound. It simply never receives the mover intents to protect.**

## 5. Conclusion & Recommendations

**Confirmed:** `all-movers` is a valid composite zone, but it only resolves fixtures whose `.zone` is `movers-left`, `movers-right`, or `movers`. Spatially-zoned movers (`front-left`, `front-right`, etc.) are silently excluded.

**Fix Options (do not implement without user direction):**

1. **Show File Fix (Data)**: Re-tag mover fixtures in the show file to use `movers-left` / `movers-right` (or `movers` for center movers). This is the fastest fix with zero code change.

2. **Hybrid Zone Fix (Code)**: Modify `COMPOSITE_ZONES` in `ZoneMapper.ts` and the `all-movers` builder in `ZoneNodeRouter.ts` to ALSO include fixtures whose fixture-type capability indicates "mover" (e.g., checking `fixture.definition.type` or capabilities), regardless of their spatial zone. This would make `all-movers` truly mean "all fixtures that are movers".

3. **LFX Track Fix (Data)**: Change the `corazon_latino.lfx` track zones from `["all-movers"]` to `["front-left", "front-right", "back-left", "back-right"]` (or whichever spatial zones the movers actually occupy).

**No code modification performed per directive.**
